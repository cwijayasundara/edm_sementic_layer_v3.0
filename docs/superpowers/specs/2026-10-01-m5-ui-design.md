# M5 — UI Design

Date: 2026-10-01. Parent spec: `2026-09-30-agentic-data-intelligence-design.md` (§4, §7, §8, §10 row M5).
Inputs: `docs/superpowers/plans/plan-4-carry-forward.md` (SSE schema, `/kpis`, `/results`, `/dev/token`).

## 1. Goal and scope
A Next.js app on `:3000` where a demo user picks a persona, sees that persona's KPI strip, asks a question in a
collapsible assistant, and gets streamed widgets on a canvas. Each widget can show the query that produced it, page
through its source rows, and be pinned into a saved dashboard that re-runs later with the *current* user's entitlements.

**In scope:**
- `frontend/` (login, workspace, KPI strip, canvas, assistant, provenance drawer, saved dashboards).
- In the agent: handle recipes on the `widget` event, recipe replay, the `/dashboards` routes, and the
  `app.saved_dashboards` migration.
- `scripts/start_frontend.sh`, Makefile targets, vitest unit tests, and a Playwright smoke test.

**Out of scope:**
- The human "verified" confirmation (thumbs up → `record_answer(verified=True)`), which moves to M6 as the
  carry-forward says.
- Semantic answer cache and evals (M6).
- Real SSO.
- Mobile layouts below 1024 px: the workspace is a desktop BI screen and only needs to degrade without breaking.

**Success:**
- The Playwright smoke passes: login → KPI strip → ask → widget renders → provenance rows → pin, save, reopen.
- The same saved dashboard opened by two personas shows each one only what it may see (per-widget `not_permitted`
  instead of data).
- No token, gateway error detail or other persona's data ever reaches the page.

## 2. Backend additions (`backend/prism/agent/`)

### 2.1 Recipes
When `ToolBox._gateway_tool` records a handle, it also records the call that produced it, as `HandleInfo.recipe`:

| Tool | Recipe |
|---|---|
| `run_metric` | `{"tool": "run_metric", "args": {"metric_id", "dimensions", "filters", "limit"}}` |
| `query_source` | `{"tool": "query_source", "args": {"source", "request"}}` |
| `combine` | `{"tool": "combine", "args": {"sql", "inputs": {"<table>": <recipe of that handle>}}}` |

- A `combine` recipe nests the recipes of its input handles. If any input handle has no recipe, the combine recipe is
  `null`.
- The `widget` SSE event gains `handle_info.recipe` (a recipe or `null`). The change is additive: older clients ignore it.
- Recipes hold only what the model sent as tool arguments. That is the caller's own query and carries no identity, so
  showing it to the caller leaks nothing new.

### 2.2 Replay (`recipes.py`)
- `Recipe` pydantic models: discriminated on `tool`, `extra="forbid"`, at most depth 3 and 8 nodes per recipe, and
  argument bounds that mirror the gateway's arg models.
- `async replay(recipe, gateway) -> (handle, summary)`:
  - Runs inputs before the combine that uses them.
  - Runs identical sub-recipes once per dashboard run, keyed by canonical JSON.
  - Calls go through `GatewayClient` with the caller's token, so the gateway (policy, SQL guard, RLS) stays the
    boundary.
  - A client-supplied recipe can do nothing the same user could not do by asking the question.
- Errors map to a widget status:
  - `not_permitted`: the gateway's final or permission codes.
  - `unavailable`: gateway down, rate limited, or a timeout.
  - `invalid`: the gateway rejected the arguments, for example a metric that no longer exists.
  - Nothing else from the gateway error is passed to the client.

### 2.3 Saved dashboards
Migration 4 creates:
```sql
CREATE TABLE app.saved_dashboards (
  id uuid PRIMARY KEY, sub text NOT NULL, title text NOT NULL, items jsonb NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now());
CREATE INDEX saved_dashboards_sub ON app.saved_dashboards (sub, created_at DESC);
```
- `APP_TABLES` and the grant step give the app role `SELECT, INSERT, DELETE` on this table only. The other app tables
  stay `SELECT, INSERT`.
- Every query filters on `sub = <caller>`.

Routes (all need the persona bearer token; errors carry no detail):

| Route | Behaviour |
|---|---|
| `GET /dashboards` | The caller's dashboards: `[{id, title, created_at, widget_count}]`, newest first |
| `POST /dashboards` | Body `{title (1..80), items: [{widget, recipe}] (1..8)}`. Each `widget` is a `Widget` from `spec.py`; its `handle` is dropped and `recipe` must parse. Max 20 dashboards per caller (`409` beyond). Returns `{id}` |
| `DELETE /dashboards/{id}` | `204`; `404` if missing or another caller's |
| `POST /dashboards/{id}/run` | Replays every item; returns `{id, title, widgets: [{widget, status, handle_info?}]}`. `status` is `ok`, `not_permitted`, `unavailable` or `invalid`; `ok` widgets carry a fresh handle and `handle_info` (columns, row_count, source, metric_id, recipe). `404` as above, `502` if the gateway is unreachable for all of them |

- Widget encodings are re-checked against the fresh columns. If a column has gone, the widget becomes a `table` over
  the same handle rather than failing.
- The store sits behind a small `DashboardStore` protocol, with a Postgres implementation and an in-memory fake for
  tests, wired in `create_app_from_env` on the existing app pool.

## 3. Frontend (`frontend/`)

### 3.1 Stack
- Next.js (App Router, TypeScript, strict), Tailwind CSS, and shadcn/ui components vendored into
  `components/ui`.
- `echarts` + `echarts-for-react`, `zod`, `vitest` (+ Testing Library), and `@playwright/test`.
- The agent base URL is `NEXT_PUBLIC_AGENT_URL` (default `http://localhost:8000`). All calls are browser → agent
  directly. CORS already allows exactly `http://localhost:3000`.
- No Vercel AI SDK. The agent's frames (`event: <type>` with JSON data) are not the AI SDK stream protocol, so a
  ~60-line SSE reader over `fetch` + `ReadableStream` is simpler and testable. This is a spec delta from §7.

### 3.2 Modules (pure, unit-tested)
| File | Responsibility |
|---|---|
| `lib/schemas.ts` | Zod mirrors of `Widget`, `Encoding`, the SSE events (`plan`, `widget`, `summary`, `telemetry`, `error`), `Recipe`, KPI tiles, result pages, dashboards |
| `lib/sse.ts` | `parseSse(stream)`: an async iterator of validated events. Handles frames split across chunks, ignores unknown event types, and treats a malformed frame as `internal_error` |
| `lib/api.ts` | Typed client: `devToken`, `kpis`, `chat` (with AbortSignal), `results`, `dashboards.*`. A `401` raises `Unauthorized` |
| `lib/session.ts` | Keeps the token in `sessionStorage`. Decodes the JWT payload **for display only** (name, scopes, rows, metrics_only, exp); the server stays the authority. Treats a token as expired one minute before `exp` |
| `lib/charts.ts` | `toEChartsOption(widget, columns, rows)`, deterministic, one branch per type: bar, stacked_bar (series pivot), line, scatter, pie, heatmap (visualMap) and kpi (single number). `table` is not a chart. Units go into axis labels and tooltips |
| `lib/format.ts` | Number formatting: `%` one decimal; `USD` compact currency; integers with grouping |
| `lib/chat.ts` | The chat reducer: turns move from `pending` → `streaming` → `done` or `error`, collecting plan steps, widgets, summary, telemetry and error |
| `lib/recipe.ts` | Recipe → display model for the drawer (metric with dimensions and filters, SQL, REST endpoint and params, combine tree) |

### 3.3 Screens and components
- **`/login`**
  - Five persona cards (name, one-line access description).
  - A click calls `POST /dev/token`, stores the token and routes to `/`.
  - If `/dev/token` answers 404, a clear note says the dev token is disabled (`PRISM_AGENT_DEV_TOKEN_ENABLED`).
- **`/` (workspace)** redirects to `/login` without a valid session. Layout: header, KPI strip, canvas, and the
  assistant on the right.
  - `Header`: the product name "Prism", the persona name, access chips derived from `scopes`/`rows`
    (e.g. "CashRecon ✓ FeedHub ✓ · region EMEA · RBAC + RLS", plus "metrics only" for the BI analyst), the dashboards
    menu, and sign out.
  - `KpiStrip`: up to 4 tiles from `/kpis`, with loading skeletons. An `unavailable` tile shows "—" and
    "Unavailable"; a `502` shows one inline notice. Tiles refresh when the page is focused again after 60 s.
  - `Canvas`: a responsive grid of `WidgetCard`s in arrival order, newest first, each tagged with the question that
    produced it.
  - `WidgetCard`:
    - Title and the chart (or table).
    - Pin and remove buttons, plus expand (a dialog with a larger chart).
    - A "view query · source rows" button that opens the provenance drawer.
    - It fetches `/results/{handle}?limit=200` once. When `row_count > 200` it says "Showing the first 200 of N
      rows".
    - A `404` (expired handle or gateway restart) shows "This result has expired. Ask again or reopen the
      dashboard."
  - `AssistantPanel`: collapsible (state kept in `localStorage`), with a question box (max 2000 chars) and a turn
    list.
    - Each turn shows live plan steps ("Running metric open_breaks…"), then the summary.
    - On error it shows the fixed message (never more).
    - A muted telemetry line shows path, tokens, cache reads and cost estimate.
    - A Stop button aborts the fetch, which cancels the run server-side.
    - A summary with no widgets (refusal or no data) shows as text only.
  - `ProvenanceDrawer` (side sheet):
    - Source, metric id, row count, and the rendered recipe.
    - A paged rows table: 50 per page, `offset`/`limit` against `/results`, with prev/next.
    - When the recipe is `null`: "Query details are not available for this result."
  - `DashboardsMenu`:
    - "Save pinned (n)" prompts for a title, then calls `POST /dashboards` with the pinned widgets and their recipes.
      Widgets without a recipe are not pinnable, and the pin control explains why.
    - Lists saved dashboards with open and delete.
    - Open calls `POST /dashboards/{id}/run` and puts the widgets on the canvas under a header with the dashboard
      title. Non-`ok` widgets render as a placeholder card stating the status ("Not permitted for your role", "Data
      service unavailable", "This query is no longer valid").
- **Visual design:**
  - Light theme with navy (`#14213d`) chrome and a crimson accent (`#b3123a`), using system font stacks.
  - One ECharts theme registered once, using a neutral categorical palette that starts with navy.
  - No client or vendor branding.
- **Errors:**
  - A 401 anywhere clears the session and goes to `/login?expired=1`.
  - Network failures show inline retry; nothing crashes the page. The canvas has an error boundary per widget.

### 3.4 State
- Client-side React state (no global store library): the session context, the canvas list (widgets plus
  pinned flags) and the chat turns.
- The canvas is in memory only. Reloading the page clears it; saved dashboards are the persistence.

## 4. Wiring
- `scripts/start_frontend.sh`:
  - Checks Node ≥ 20 and runs `npm ci` when `node_modules` is missing or older than `package-lock.json`.
  - Then runs `next dev -p 3000`.
  - Warns (does not fail) if the agent `/healthz` is not answering.
- `Makefile`:
  - `make frontend` runs the script.
  - `make test-ui` runs `npm run lint`, `npm run typecheck` and `npm test` (vitest).
  - `make e2e` runs the Playwright smoke.
- README: a "UI" section.

## 5. Testing
- **Backend (pytest, default suite, stack-free):**
  - Recipe capture for each tool, including nested combine and a combine with an unknown input.
  - The widget event carries the recipe.
  - `Recipe` validation bounds (depth, nodes, unknown keys).
  - Replay against `FakeGateway`: order, dedupe, error → status mapping, and column drift → table.
  - `/dashboards` routes with the in-memory store: ownership (404 across callers), limits, 401, and run statuses.
  - The migration test covers the new table and the narrower grant.
- **Backend live (deselected by default):**
  - Saved dashboards are owned per `sub`, so cross-persona sharing does not exist. Instead, the test saves a
    `cash_ops_emea` dashboard holding one `cashrecon` recipe and one `refmaster` recipe (a client can submit any
    recipe).
  - On run, the first is `ok` with EMEA rows only and the second is `not_permitted`.
- **Frontend (vitest):**
  - The SSE parser (chunk splits, multiple frames per chunk, unknown events, malformed JSON).
  - Zod schemas against the carry-forward examples.
  - `toEChartsOption` per widget type (golden option snapshots).
  - Formatting, the chat reducer and recipe rendering.
- **E2E (Playwright, `make e2e`):**
  - Runs against `next dev` with the agent mocked through `page.route`, using fixture SSE bodies and JSON, so it needs
    no API key or stack.
  - Flow: login → KPI tiles → ask → plan step → bar widget renders → provenance drawer pages rows → pin → save →
    reopen.
  - With `PRISM_E2E_LIVE=1` the same spec runs against the real agent, checking only that the KPI strip and login
    work, because the chat needs a key.
