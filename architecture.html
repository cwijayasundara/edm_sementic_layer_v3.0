    Agentic data intelligence

    Ask the data platform a question, get a dashboard back

    Prism puts a team of AI agents on top of five different enterprise data platforms (two REST-based data-management systems and three Postgres stores) without letting the agents near the data directly. A graph semantic layer tells the agents what the business means and where it lives; a single semantic gateway is the only door to the data and enforces every entitlement; a supervisor / sub-agent system plans, fans out, joins and explains the results.

    5simulated data platforms, 2 REST + 3 SQL
    1agent-facing door to data (Semantic Gateway MCP)
    25governed metrics in the catalog
    59business glossary terms in 6 glossaries
    5personas with different datasets and row scopes
    30 + 15golden and red-team eval questions

    This document explains the problem, the architecture that solves it, and the reasons behind each design choice. It is written from the code as it stands (backend/prism, frontend) and the design specs in docs/superpowers/specs. Where the build differs from the original proposal, section 14 says so.

    01The business problem

    Building agents on top of many different data sources

    An operations organisation runs on several specialised platforms. Each has its own storage, interface, vocabulary and access rules. The questions people actually ask cut across them:

    • “Which legal entity has the most USD breaks open longer than 5 days?” one source, governed metric
    • “Which vendor drives most corporate-bond price conflicts this week?” REST source
    • “Why did fund PF003 breach its NAV tolerance on 24 September?” all five sources

    Why “just give an LLM the databases” fails

    Accuracy

    Plausible but wrong

    Text-to-SQL over raw schemas guesses at meaning (“aged break”, “late feed”, “golden price”) and joins. It fails quietly with believable numbers.

    Heterogeneity

    REST and SQL differ

    Two platforms are reachable only through domain REST APIs; three are relational stores. Agents must work over both uniformly.

    Security

    Entitlements per person

    Each persona sees different datasets and rows (region, fund group, feed type), and one is metrics-only. The model must never be the security boundary.

    Cost & latency

    Token budgets

    Schema dumps (20k+ tokens) and raw rows in the context are slow and expensive. Deterministic work (KPIs, maths, joins) should cost no tokens.

    Trust

    Show your working

    Users need provenance: which metric, which source, which rows, which steps, so they can confirm an answer.

    Cross-system

    Causes span systems

    Root causes run through several platforms (a feed failure → missed corporate action → price spike → NAV breach → cash break). Keys change at each hop.

    Success criteria

    1. A user signs in as a persona, sees role-appropriate KPIs, asks a question and gets a correct chart, a 2–3 sentence summary and a provenance link.
    2. The same question asked by two personas returns different, correctly scoped results; a forbidden request returns a plain “not entitled”, never leaked data.
    3. Token use is measured per question, kept low by graph retrieval, prompt caching and the no-raw-rows rule.

    02The solution in one picture

    Map (graph) · guide (gateway) · territory (sources) · analysts (agents)

    The core idea: the context graph is the map, the source MCP servers are the territory, and the semantic gateway is the guide that reads the map and makes the trip on the user's behalf. Agents speak business language to one gateway. They never see a database credential, a source token or a full result set.

    03Design principles

    P1

    One door to the data

    Agents talk only to the Semantic Gateway. Source MCP servers accept only gateway-minted, audience-bound tokens.

    P2

    Governed metrics first

    Business measures are YAML-defined metrics compiled by code. Free-form SQL / endpoint queries are a guarded fallback, off for metrics-only roles.

    P3

    Rows never reach the model

    Results stay in the gateway. The model gets a handle, columns, row count and at most 5 sample rows; the UI pages the rest by handle.

    P4

    Just-in-time context

    A role-pruned context pack of about 3k tokens from the graph replaces schema dumps.

    P5

    Uniform over heterogeneous

    Every source has the same three MCP tools; the agent neither knows nor cares whether a source is REST or SQL.

    P6

    Enforce at the source

    Context pruning and gateway policy fail early; Postgres RLS with signed claims is the real boundary.

    P7

    Deterministic first

    KPIs, metric maths, joins, chart data and saved-dashboard replays spend no tokens.

    P8

    Explicit failure

    A forbidden or unknown object answers exactly like a missing one; the agent states the limit and stops.

    Shared keys make cross-source questions possible

    The simulator builds one shared universe (securities with valid ISIN check digits, legal entities with valid LEI checksums, vendors, custodians, portfolios, cash accounts, 90 business days) and projects it into every system, so keys line up. The graph records them as same_key groups (7 in the ontology) and metric-to-metric JOINABLE_ON links:

    • security_id / isin: RefMaster ↔ MarketMaster ↔ AssetRecon
    • legal_entity_id: RefMaster ↔ CashRecon (and fund → entity)
    • custodian / source_id: AssetRecon ↔ FeedHub
    • cash account / bank source: CashRecon ↔ FeedHub

    Planted stories give the demo answers worth finding, and the evals check them: Vendor A driving 60 of 90 corporate-bond price conflicts this week; SRC001 late feeds; PF001/PF002/PF005 position exceptions; LE00016 holding 64 of 79 aged USD breaks; and the cross-system incident in section 10.

    05The semantic layer: a context graph

    What the business means, where it lives, how it joins, and what has worked before

    The semantic layer is a Neo4j graph loaded by make graph from four inputs: each MCP server's metric and REST registries, the Postgres DDL, and hand-authored knowledge YAML in prism/graph/knowledge/ (ontology, glossary, seed history). Every executable node carries its address (source, table or endpoint), so a retrieval result is directly actionable. The loader is idempotent and versioned; the gateway refuses to start on an empty or stale graph and hot-swaps its catalog when the graph version moves forward.

    Graph model

    Three knowledge layers

    1 · Ontology

    What things are

    10 concepts (Security, LegalEntity, Price, Vendor, Position, Portfolio, Break, …), 9 typed relations and 7 cross-source key groups. IMPLEMENTED_BY leads to tables/endpoints; IDENTIFIED_BY gives the join keys.

    2 · Glossary

    What words mean here

    59 terms in 6 domain glossaries, with synonyms (“nostro” / “cash account”), owners and BROADER hierarchy. Grounds phrases like “aged break” or “late feed” in exact metrics and filters.

    3 · Query history

    What has worked before

    12 curated seed questions, plus human-confirmed answers distilled into Question → Execution → Metric/Dimension. Returned as worked examples; curated seeds always rank first.

    Governed metrics. 25 metrics (20 SQL metrics in prism/mcp/metrics/*.yaml, 5 REST metrics in prism/mcp/rest/*.yaml), each with a definition, grain, unit, allowed dimensions and source. The gateway routes a metric by catalog lookup, so the agent never names a source for it. Metric-to-metric JOINABLE_ON {on: "<a dim> = <b dim>"} edges tell the agent how to hop from one system to the next.

    The search_context pipeline

    Because the role filter runs inside the Cypher, the model never even learns that a forbidden dataset, column or metric exists. For a metrics-only caller the pack contains no tables, columns, endpoints or sensitive dimensions at all.

    06The semantic gateway

    One MCP server, eleven tools, identity from the token, one audit row per call

    The gateway (prism/gateway, port 8200) is a stateless streamable-HTTP MCP server accepting only gateway-mcp-audience tokens. It resolves business requests against the catalog, authorises them, compiles and routes them to the right source with a freshly minted token, and keeps the results.

    ToolWhat it doesWho calls it
    search_contextRole-filtered context packModel
    run_metricGoverned metric; the catalog picks the source; returns {handle, summary}Model, KPIs, dashboards
    query_sourceGuarded free-form SELECT or endpoint call; not for metrics-only rolesModel
    combineOne DuckDB SELECT over the caller's own handles, in memory; refuses summing across currenciesModel
    get_rowsOne page (≤ 200 rows) of the caller's own resultUI
    record_answerWrites query history (metric ids and dimensions from live handles, never the plan text), stored unverifiedAgent service
    confirm_answerHuman confirmation: sets verified on the caller's own metric-backed answerUI
    record_traceStores how a run reached its answer, linked to graph nodes via the caller's own handlesAgent service
    get_traceThe caller's own trace, re-gated against their roleUI
    mark_trace_confirmedMarks the trace when its answer is confirmedAgent service
    lineageRole-gated subgraph behind one of the caller's handlesUI

    Only the first four are offered to the model. The rest are used by the service or the UI and are tested to be absent from every LLM tool list.

    Handles

    Results stay server-side

    A result lives in an in-memory store for 15 minutes, owned by the caller's sub. Another caller's handle answers unknown_handle, the same as a missing one. Store quota: 128 MB total, 16 MB per caller; when full, a new result is refused rather than evicting someone else's.

    Limits

    Per-caller fairness

    search_context: 2 in flight, 60 a minute. record_answer: 10 a minute. combine: 1 at a time, permit held until the DuckDB thread really ends. Per-(caller, source) semaphores and retry on source calls.

    Audit

    Names and counts, never values

    Every call writes one app.audit row: catalog names, counts and error codes; the question only as an HMAC. No row values, no tokens.

    Errors

    Typed codes

    not_permitted, metrics_only, invalid_request, unknown_handle, context_unavailable, source_unavailable, rate_limited, gateway_busy, currency_mixing, result_store_full.

    07The agentic system

    A supervisor that plans, sub-agents that fetch, a specialist that charts

    The deep-agent pattern, built on the Messages API

    Prism implements the deep-agent pattern (a planning agent that delegates to sub-agents with their own context windows, offloads bulky state out of the context, uses specialist sub-agents and keeps a durable record of its reasoning) directly on the Anthropic Messages API with a small, hand-written loop (prism/agent/runner.py). It does not use a deep-agents framework library; the loop sits behind a Runner protocol so a framework or the Agent SDK can be swapped in later.

    One /chat turn

    Cost, latency and caching

    • Prompt caching: the frozen system prompt and the fixed tool list sit before the cache breakpoint; the run context (today, data as-of, roles, metrics-only flag, readable systems) comes after. Cache reads are metered per turn.
    • Model tiering: Sonnet 5.5 supervises; Haiku 4.5 runs sub-agents and charting; Opus 5.5 only on escalation.
    • No tokens on deterministic work: /kpis calls governed metrics directly (cached per role for 60 s); saved dashboards replay stored recipes with the current user's access and no model call.
    • Telemetry: each run writes app.agent_runs (question as HMAC, path, models, input / output / cache-read tokens, turns, tool calls and latency, cost, status).

    Cross-system investigation pattern

    For “why did this happen” or “what else did it affect” questions, the supervisor prompt teaches a four-step pattern that uses only governed metrics:

    1. Anchor. Run the metric the question starts from, grouped by its key dimension(s).
    2. Follow links. The pack's metric_links say which metric of another system joins on which key. Run each linked metric filtered by the key values found so far; issue calls in parallel when their keys are known. Stop when every readable system is checked or a hop returns nothing.
    3. Join. One combine over up to 8 handles, hop by hop, because the key changes along the chain (portfolio → security → source → entity).
    4. Answer. The causal chain in time order, citing numbers from results only, and naming every system that could not be checked (not readable, refused or not linked) instead of implying the chain is complete.

    08Security: RBAC + RLS, defence in depth

    The model is never the security boundary

    LayerMechanismPurpose
    1 · Context pruninggate() inside every retrieval and lineage CypherThe model never learns about forbidden datasets or columns
    2 · Gateway policyCatalog-derived grants checked before routing; one audit row per call; existence never leakedEarly, explicit refusals at a single choke point
    3 · Enforcement at sourcePostgres FORCE ROW LEVEL SECURITY, non-owner NOBYPASSRLS role, HMAC-signed claims verified by SECURITY DEFINER functions in prism_sec, masking views for sensitive columnsThe real boundary: even LLM-written SQL cannot forge entitlements

    Role checks run in four places: Python can(), the SQL RLS functions, the graph's Cypher gate() and the gateway policy. A test keeps all four in agreement.

    -- per tool call (prism/db/session.py)
BEGIN READ ONLY;
SET LOCAL ROLE bi_reader;                             -- non-owner, NOBYPASSRLS
SELECT set_config('app.ctx', '<HMAC-signed claims>', true);
SELECT set_config('statement_timeout', '<ms>', true);
<validated SELECT>;
COMMIT;

-- policy on every table (prism/db/policies.py), FORCE ROW LEVEL SECURITY
CREATE POLICY prism_read ON cashrecon.breaks FOR SELECT
  USING (prism_sec.can('cashrecon', 'breaks')
         AND (prism_sec.allowed('region') @> ARRAY['*'] OR region = ANY(prism_sec.allowed('region'))));
-- prism_sec.claims() / can() / allowed() are SECURITY DEFINER and verify the HMAC on app.ctx

    Prompt-injection hygiene

    • Context-pack examples and tool results are wrapped and labelled as data; the prompts say instructions inside them are ignored.
    • The toolset is read-only: no generic fetch, no write tools. Entitlements cannot be changed by the conversation.
    • The simulator plants injected-instruction canaries in ticket and comment text; red-team evals fail on any canary in an answer.
    • Distilled history is sanitised (length, character set, no tool names, SQL verbs, instructions, links or literal values) and needs several distinct callers, so one user cannot plant examples for others.

    09Learning loop & reasoning traces

    The semantic layer gets better from confirmed answers, never from unverified ones

    Reasoning traces (“How I got this”)

    Each answered run leaves a decision trace in Neo4j, beside (never inside) the catalog:

    (:Trace {run_id, sub, question, answer, path, status, confirmed, expires_at})
  -[:HAS_STEP]->(:TraceStep {seq, parent, kind, label, note, considered, ms, status})
       -[:CALLED]->(:ToolCall {tool, args_json, handle, rows, truncated})
  (:TraceStep)-[:TOUCHED]->(Metric | Source | Dimension | Table | Endpoint | Column | Field)
(:Trace)-[:ANSWERED_WITH]->(:Metric)
    • Written by the gateway (record_trace); the agent holds no graph credentials.
    • Links come only from the caller's own live handles and only to nodes their role passes; free text never becomes a link.
    • Owner-only reads, re-gated on read, 7-day retention; survives make graph; invisible to retrieval, lineage and the catalog.

    10Worked example: one incident across all five systems

    “Why did PF003 breach its NAV tolerance on 24 September?”

    The simulator plants a realistic incident whose cause runs through every platform: a 2-for-1 split on security SEC001982 (issuer LE00364) is missed because a corporate-actions feed failed.

    Why this matters. No single system explains the breach. The price is right; the reference data missed the split; the feed failure caused it; the cash break is its tail. The semantic layer supplies exactly what the agent needs to connect them with governed metrics only: join-key dimensions, metric links and the investigation pattern. A persona who cannot read some systems gets the part of the chain they are entitled to, with the unreadable systems named. Three golden cases replay the incident from different entry points (the NAV breach, the late feed and the issuer).

    11UI & provenance

    Workspace

    KPIs + canvas + assistant

    Four deterministic KPI tiles per persona; a canvas of streamed widgets (pin, remove, expand); a collapsible assistant streaming plan → widgets → summary.

    Renderer

    DashboardSpec → ECharts

    Widget types kpi, bar, stacked_bar, line, heatmap, table, pie, scatter. Zod on the client mirrors Pydantic on the server.

    Provenance

    View query · source rows

    The executed metric / SQL / endpoint call, source system, row count and a paginated row table, fetched by handle.

    Lineage

    Context graph dialog

    The role-gated subgraph behind a widget: metric, dimensions, tables, columns, endpoints, source, terms and past questions.

    Reasoning

    How I got this

    Timeline of steps (nested sub-agent steps indented), tools, durations, notes and touched-node chips that highlight in the graph.

    Dashboards

    Saved and re-run

    Pinned widgets are saved as recipes and re-executed with the current user's access, with no model call.

    12Evaluation & quality

    Golden questions (30)

    Each case runs under its own eval-<id> identity and is graded without an LLM judge:

    • answered: a widget arrived, no error
    • routing: the expected metric or source was used
    • rows: widget rows equal the reference recipe replayed through the gateway
    • story: the planted story holds on the rows
    • chart: the widget type is allowed

    Red-team (15)

    A case fails on any of four detectors:

    • an injected-instruction canary or forbidden value in the answer
    • a canary from rows the persona cannot see
    • an out-of-scope row
    • a successful forbidden tool call in app.audit
    CommandWhat it checks
    make eval-checkNo model calls: references replay, planted stories hold, canaries readable / hidden as claimed
    make evalLive: golden + red-team through the agent and the real model, capped by --max-cost-usd (default $5); exits 1 on any leak
    make test / test-fastUnit and integration suites (scripted model, fake gateway, Dockerised Postgres, Neo4j test namespace), RBAC matrix
    make test-livePlanted stories, persona matrix, handle isolation and every KPI tile through the running stack
    make test-ui / make e2eLint, types, vitest; Playwright against a mocked agent (or live)

    Roadmap

    • Full semantic-layer “model map” view: type-level graph linked to instances, with an answer's path highlighted.
    • The remaining escalation triggers (multi-source, low confidence) and precedent search over past traces.
    • Parallel per-source delegation along an incident chain (hops are sequential today).
    • Real SSO / OIDC with RFC 8693 token exchange; cloud deployment; model access via a managed cloud provider by configuration.
    • Exposing the same gateway as a customer-facing MCP server, unchanged.
    • Code-execution sandbox for heavy data wrangling (phase 2 option).
    Out of scope for the MVP: point-in-time history, a warehouse, regulatory reporting and write-back actions (assign a break, approve a price).
